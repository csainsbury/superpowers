# Model Selection

Part of superpowers:subagent-driven-development and executing-plans.

Use the least expensive sufficiently capable authorised model and the smallest
sufficient context for each role. Prefer available authorised subscription
routes when capability, privacy and reliability suffice. API/SDK transport is
not a billing class; unknown charging routes fail closed with an actionable
explanation. Version identity alone neither bans nor approves a model.

**Mechanical implementation:** use a fast sufficient route for clear, bounded
specs. **Integration, architecture and design:** select for demonstrated needs,
not an automatic maximum tier. Multi-file scope alone does not prove a gap.

**Review:** choose an independent sufficient reviewer for size, complexity and
risk, including final whole-branch review. Subtle concurrency/security changes
need a reviewer able to judge those risks, not necessarily the most expensive
model. Re-review only concrete fix findings under the authorised review cap.

**Escalation:** require a demonstrated capability gap or the user's explicit
choice, record the reason, and stay within route/budget authority. Fresh context
or clearer evidence may resolve a blocked fix without a cost increase; round
number alone does not justify escalation. Never silently switch provider, enter
paid inference or select a higher-cost model after a failure. Preserve exact
scoped exceptions and app-owned caps; no exception grants general provider use.

Specify the authorised model explicitly when dispatching; inheritance may select
an unintended route or cost. Judge total context, turns, wall-clock and quality
from evidence rather than asserting a fixed tier is always cheaper. Keep current
configured defaults unless the active instruction authorises changing them.
